## 1 如何用三十秒介绍这个设计

> 我们是一个持续多轮教学的学习 Agent。我把跨会话记忆落地为两类：一份短学生记忆，以及每个会话一份学习经历，两类正文都由模型提取和整合。目标和子目标只在当前会话结构化保存。每次模型调用前都计算输入预算，达到软水位且有收益时压缩，预测增长接近预防线时必须降载。压缩只处理已提交、工具闭合的历史，当前原话、原题、帮助条件和目标从业务状态完整注入；摘要有来源、版本检查和失败回退，超预算就拒发。

结构化字段、来源和版本可以做确定性校验，摘要是否完整表达原意仍需测试、来源回查和人工标注，不能承诺“所有历史含义都不会丢失”。

## 2 如果面试官要求两分钟展开 怎么回答

> 我先区分三种东西。第一是跨会话的学生记忆，用于个性化：长期学生记忆保存稳定偏好和学习特征，长度目标是 600 Tokens，上限 800 Tokens；学习经历与会话一一对应，保存这次学了什么、哪些地方卡住、使用过哪些帮助以及未解决的问题。它们由模型提取，服务端负责来源、身份、长度和版本校验。
>
> 第二是会话内的业务状态：目标、子目标、当前节点、暂停原因、待答问题和返回位置。这部分结构化保存，模型可以提出变更，但数据库中的状态才是后续调用的依据。历史会话中的未完成事项可以作为建议，新会话不会自动恢复旧目标。
>
> 第三是发给模型的工作上下文。Runner、工具循环和模型共享出口都有预算检查。默认软水位为可用输入预算的 70%，预测输入加增长达到 90% 时必须处理，55% 是回落目标。实际会先去重，把旧教学记录交给模型摘要，必要时降低本次输出预留或关闭新工具调用，再重新计数；不会为了达到固定压缩率截断学生当前答案。
>
> 安全点的意思是相关业务记录已经保存，工具调用已经取得终态回执。我们不会把还没有完成的工具调用和结果拆开，也不会为了压缩取消一个副作用不明的操作。摘要生成后还要检查目标 ID、待答题、原始答案引用和状态版本。校验失败就保留旧上下文，重新生成或者进入受控失败。
>
> 已增加对应测试和真实后端验收，例如补基础后返回原题、同一会话只有一份经历、当前原话和帮助条件保持完整、摘要不修改掌握度。当前 Token 使用保守估算，增长采用冷启动加指数平滑；阈值还没有校准，也没有长期学习效果和费用收益结论。

## 3 现在已经实现了什么 哪些还是设计

以下是当前源码可以核查的实现，尚未验证的部分单独列出。

| 内容 | 当前可核查的实现 | 明确边界 |
|---|---|---|
| 长期学生记忆 | `StudentMemory` 短正文，模型提取与合并，来源、长度和版本校验 | 没有复杂画像、精确条目删除或向量记忆索引 |
| 学习经历 | `SessionExperience` 以 session_id 唯一，单调事实水位、后台任务、provisional/final | 断线不等于结束，历史经历不自动变成新会话任务 |
| 会话目标 | 稳定节点 ID、父子关系、依赖、成功标准、状态、补救返回栈与版本校验 | 目标只在本会话执行，活动完成不等于掌握 |
| 上下文构建 | 统一固定任务与历史投影，旧记录和重复记忆去重 | 当前原话、原题、帮助条件不能任意截字 |
| 预算与压缩 | 每轮工具和 JSON 修复前守卫，实际模型分块摘要、源指纹检查点与失败回退 | 使用保守估算与 EMA，默认阈值未校准，未证明语义零遗漏 |
| 记忆维护 | 工作台/API 支持整理、纠正、遗忘和撤销屏障 | 普通自然聊天尚无专门记忆管理工具；当前仍为本地身份模式 |

原版本源码入口涉及记忆服务、后台任务、会话目标、上下文构建与旧 `agent/context/compactor.py`；旧压缩器已经删除。当前路径统一看[源码阅读顺序](../learning_harness/06_source_reading_guide.md)，避免把下文历史机制当作仍可执行的底座。

可以说“在原始记录和续学状态基础上，实现了轻量模型记忆、会话目标和按预算压缩”。当前实现不包括分布式任务调度、任意工具副作用恢复或生产规模容量保证。

## 4 为什么只做两类跨会话记忆

业务目前只需要回答两个问题：**这个学生通常怎样学习，以及过去这次会话经历了什么**。

长期学生记忆服务于讲解方式和练习安排，要求短、稳定、便于整份读取；学习经历记忆服务于追溯和相关历史召回，允许按会话累积。二者有不同的更新速度与读取方式，放在同一份不断增长的文本中容易混淆。

当前目标树是一次教学活动的执行状态，不要求跨会话延续。教材、题库和知识图谱属于课程知识资源，也不算第三类学生记忆。上下文检查点是运行时派生物，不应因为存进数据库就再命名为一种长期学生记忆。

第一阶段不需要把“记忆层数多”当作设计优点，优先把边界、更新规则和验证做完整。

## 5 两类记忆具体存什么 如何保持简单

当前业务结构如下，实际字段见 [记忆模型](../../backend/app/domains/memory/models.py)。

| 对象 | 主要内容 | 最少需要的维护信息 |
|---|---|---|
| 长期学生记忆 | 学生明确偏好、稳定的学习特征、与教学有关的持续约束 | 学生 ID、短文本或少量条目、来源引用、版本、更新时间 |
| 会话学习经历 | 学习范围、关键困难、采用的教学方式、作答和帮助条件的概述、未解决问题 | 唯一会话 ID、摘要、来源引用、处理水位、版本、更新时间 |

长期记忆正文目标 600 Tokens，上限 800 Tokens；学习经历正文目标 1200 Tokens，上限 2000 Tokens。这里约束的是模型可读正文，来源、版本等元数据仍需要保留，组装请求时也要计入实际输入。

长期记忆不保存整段聊天、每道题的详细过程或无限增长的知识点清单。某个学生“在两次去括号练习中漏了负号”首先属于学习经历；是否升级成稳定学习特征，需要结合更多证据。能力状态仍由已有的作答和评估机制维护，不能由记忆摘要直接改写。

## 6 既然由模型自己提取 代码还负责什么

模型负责**语义工作**：判断哪些内容值得记、合并同义表述、区分稳定特征与本次现象、生成短摘要。服务端负责**提交边界**：在什么事件后运行、输入哪些已提交记录、允许改哪些字段，以及怎样校验和保存。

一次提取的输入包含旧记忆、尚未处理的新证据和明确的输出契约。输出至少包含建议的新正文、所依据的消息或作答 ID，以及相对于旧版的变化。服务端检查身份和课程归属、来源是否存在、版本是否匹配、文本是否超限，再提交新版本。

这样“模型自动提取”不会变成“模型可以修改任何数据库字段”。记忆提取器没有修改掌握度、提交答案或执行教学工具的权限。来自学生聊天和历史资料的指令也只能作为待分析内容，不能改变提取器的系统规则。

对于“有来源”的判断还要区分两层：程序可以检查 ID 真实存在、属于该学生，却不能仅凭 ID 存在就证明摘要语义正确。是否曲解原文需要进一步检查和离线评测。

当前维护链路已有真实后端验证，但人工抽检曾见长期正文混入“尚无独立作答记录，掌握情况待观察”。这种本次评估状态不应成为稳定学生特征，说明提示词限制仍可能失效。当前没有独立的逐条语义审查器，不能把来源与长度校验通过说成长期记忆语义已经全部验证。

## 7 学习经历与会话一一对应 那长会话怎么更新

“一一对应”指一个会话只有一份当前有效的经历记忆，不是必须等会话彻底结束才生成，也不是每完成一个子目标就新增一份经历。

初始触发规则是累计五个完整业务轮次或新增事实约 3000 Tokens 后合并一次后台更新；子目标完成、补救返回、显式目标变更时优先刷新。明确结束时刷新到当前事实水位并标记 final，空闲三十分钟且有新事实时只刷新 provisional，不视为会话结束。每次只处理尚未覆盖的已提交记录，同时读取旧摘要，生成新的完整经历摘要，再替换这一行的有效版本。会话唯一约束防止重试时产生多个有效经历。

经历中保留 `covered_seq`，表示目前覆盖到哪条已提交记录。实现新增了 `MemoryFact.seq`，在会话内单调递增，并对会话与来源引用设置唯一约束，不靠时间戳或 UUID 排序。提交拒绝水位回退，final 还需匹配会话结束版本，避免旧收尾任务覆盖重新打开后的 provisional 状态。

同一个会话被学生隔天继续使用时，仍更新同一份经历；新建会话才对应另一份经历。断开 SSE 或关闭浏览器不标 final。提取器按带来源、水位和片段序号的数据分批读取，原始答案仍完整保存；片段总结的语义质量还需要评审。当前事件与触发链见 [实现说明](../stem_v1/17_memory_and_context_implementation.md)。

## 8 长期学生记忆怎样自动总结 去重与压缩

采用“读取旧版并生成新版”。提示词要求没有实质变化时返回 `no_change`；服务收到后不重写该正文，经历水位和生命周期状态仍可推进。代码不假称能够独立识别所有语义等价改写。

模型读取旧学生记忆、旧经历和新增事实，同次提取产生两类候选，只保留与未来教学有关、相对稳定的内容。提示词要求合并同义偏好、按明确纠正修订旧说法、将一次性困难留在经历里。新版本正文仍必须满足长度上限，这些语义要求需要额外抽检。

例如旧版是“偏好先看例子”，新版证据是“学生明确要求先给一个反例，再讲抽象定义”。模型可以改为“讲抽象概念前先用例子或反例说明”，而不必保留两条高度重复的句子。但如果新证据仅来自一次临时请求，就不宜泛化成永久偏好。

超过上限时让模型按保留优先级定向重新整合一次；重新生成仍不合格就不提交。不能通过机械截掉正文末尾来冒充完成语义整合。旧版仍可用，新任务保持待重试状态。

长度合格和语义归类正确是两件事。当前靠提示词区分长期特征与本次经历，尚未用独立条目审查保证分类；人工抽检发现的“将临时评估状态写入长期正文”需要继续改善和评测，不能以自动总结替代语义验收。

## 9 模型记错了 偏好变化了 学生要求删除怎么办

先区分记录错误和学生发生变化。前者更正原判断，后者保留必要版本信息并让新版生效。最新学生明确表达与原文证据的优先级，高于旧摘要中的推断。

当前通过工作台和 `/memory/correct`、`/memory/{kind}` API 维护记忆。纠正先撤销所选类别的旧正文，再让模型依据纠正指令重建；遗忘粒度为学生记忆、该会话经历或两者，不是逐条偏好精确删除。普通聊天尚未开放专门的记忆管理工具，不能声称一句自然语言删除要求已经覆盖完整维护协议。

实现保存来源撤销列表、时间屏障和失效版本，后续提取过滤被撤销来源，上下文检查点按撤销指纹失效。后台旧任务不能覆盖纠正后的新状态。当前没有向量记忆索引，因此也不宣称已经实现向量索引删除。遗忘记忆不删除原始作答；删除原始数据属于单独范围。

删除作业提交后，旧版本提取任务必须因版本或删除标记变化而放弃提交，不能在删除完成后又写回旧内容。

## 10 要不要一开始就使用向量数据库

目前没有必要为了“有记忆”先上独立向量库。

长期画像很短，可以按学生直接读取整份；学习经历先按学生、课程、时间和知识点等结构化条件筛选，再在有限候选中选择相关经历。以后会话积累较多、关键词检索明显漏召回，再评估语义检索。

如果引入向量检索，身份和权限过滤必须在候选生成阶段生效，不能先检索全体学生再让模型判断归属。数据库中的记忆版本仍是依据，向量索引只是检索投影，更新和删除也必须同步。

面试中不需要把 Redis、向量库、关系数据库全部列出来。应先解释访问模式与规模，再解释为什么选择相应存储。

## 11 会话内的目标体系为什么需要结构化

因为目标不仅是给模型看的自然语言，还决定本轮在推进什么、临时任务结束后回哪里。

最少保存会话 ID、目标 ID、父目标 ID、目标描述、成功标准、状态、当前节点、必要依赖和返回位置。模型提出目标拆解和变化，服务端校验引用和状态迁移后保存。当前目标的版本也进入上下文检查点。

例如“解一元一次方程”下有“去括号”“合并同类项”等子目标；学生去括号时卡在负数乘法，可以暂停原子目标并建立补基础任务。补基础结束后根据返回关系恢复原题，不能靠模型从一段很长的聊天中猜测。

活动完成与能力掌握分开表示。完成一轮讲解可以使教学步骤完成，但不自动证明学生掌握去括号。`continuation` 继续保存接续说明，`SessionGoalState` 另行保存并校验节点和返回栈；两者在业务提交时关联，不把字符串步骤当成完整目标图。

## 12 新会话读到了历史未完成目标 会自动继续吗

不会。跨会话读取到的是“上次还有一个问题未解决”的经历信息，不会把旧目标节点复制成新会话的活动目标。

模型可以建议“上次还有去括号练习未完成，是否继续”，但学生当前请求和当前会话目标优先。学生明确要求接着学时，由本会话新建目标节点，并引用历史经历作为背景。这样同时满足“有连续学习体验”和“目标仅在会话内维护”。

同一会话的目标切换也要区分临时追问、补基础和明确更换整体目标。压缩不能把暂停写成完成，也不能让已经放弃的目标重新变为活动状态。

## 13 续学上下文包具体包含什么

每次模型调用先构建一个与角色有关的输入投影，而不直接发送所有历史消息。

| 部分 | 用途 | 主要来源 |
|---|---|---|
| 当前任务契约 | 当前请求、原题、待答问题、帮助条件、必要约束 | 当前业务状态和相关原始记录 |
| 目标导航 | 整体目标、当前子目标、祖先、暂停与返回关系 | 当前会话的结构化目标 |
| 学习状态 | 有关的真实作答与评估，保留不确定性 | 原始证据和学习状态服务 |
| 相关记忆 | 短学生画像、相关会话经历 | 两类跨会话记忆 |
| 阶段摘要 | 已结束过程中的关键尝试、分歧和未解决事项 | 带来源的会话检查点 |
| 近期原文 | 保持最近对话表达和局部推理的连续性 | 近期完整交互单元 |

角色不同，输入也不同。教学 Agent 通常只需要当前子目标；主 Agent 需要目标导航；评估 Agent 需要原题、真实答案与帮助条件，不能拿教学摘要替代评估材料。

“必保留”指业务上不可省略的内容，而不是无限大的字段必须一次性塞进请求。若必保留内容本身超预算，要拆任务或停止该次调用，详见第 20 问。

## 14 什么时候允许压缩 什么时候必须压缩 什么时候暂时不允许

判断既看容量，也看状态。三个条件不能混为一个“聊了很多轮”。

| 情况 | 判断 | 动作 |
|---|---|---|
| 存在已提交的完整历史前缀 | 允许生成候选摘要 | 当前实现只在模型调用前执行，校验后替换消息 |
| 当前输入达到软水位，预计回收量达标，且处于安全点 | 建议主动压缩 | 在自然学习片段边界采用校验通过的摘要 |
| 预测下一轮输入达到硬预防水位 | 必须处理容量 | 安全时压缩；暂不安全时等待已有业务到终态，再压缩 |
| 下一次实际输入超过允许输入预算 | 禁止发起这次模型请求 | 必须先收缩、拆分或受控失败 |
| 工具副作用状态未知、作答尚未提交、目标版本正在变化 | 暂不允许提交压缩检查点 | 先取得回执、完成提交或读取新版本 |
| 输入未达软水位且没有必要维护事件 | 一般不压缩 | 避免无收益的额外摘要调用 |

允许描述安全性，软硬水位描述必要程度。当前上下文摘要在模型调用前同步生成，没有另建后台压缩 worker；后台记忆 worker 是另一条链路。工具组闭合、事实提交和版本校验后才能替换消息。“必须处理”不等于强行覆盖摘要，也不允许超预算再发一轮；已执行的工具先取得终态回执，下次模型调用仍必须通过守卫。

等待学生输入本身是可以压缩的时机，前提是待答题、题目版本、已给帮助和返回位置已经保存。不能把“有待答题”一概当成禁止压缩的理由。

## 15 Token 预算怎么计算 为什么不是按轮数或字符

设模型厂商允许的窗口为 \(W\)，独立输入上限为 \(P\)，项目配置的单次工作容量为 \(C\)，最大输出预留为 \(O\)，计数误差、协议开销等安全预留为 \(S\)。要求 \(C\leq W\)，实际可用输入预算为：

\[
H=\min(P,C-O-S)
\]

没有独立输入上限时忽略 \(P\)，如果 \(H\leq0\) 则配置无效。\(C\) 是成本、延迟和模型使用方式共同约束的工程上限，可能明显小于厂商最大窗口。模型思考等额外预算如适用，应按照实际接口的计费和窗口规则一并纳入配置，不能假定对所有模型都相同。

对当前最终待发送输入进行计数或保守估算，记为 \(T\)，初始策略为：

\[
\text{软水位}=0.70H,\qquad
\text{硬预防水位}=0.90H,\qquad
\text{压缩目标}=0.55H
\]

例如仅作算术说明，若 \(C=32768\)、\(O=4096\)、\(S=2048\)，且 \(P\) 不更小，则 \(H=26624\)，软水位约 18637、硬预防水位约 23962，压缩后目标约 14643 Tokens。该例不是模型选型或已经实测过的生产配置。

计入系统指令、工具与输出 Schema、消息、记忆、资料和多模态输入。当前 `weighted_unicode_v1` 按 ASCII 每字符 0.5、非 ASCII 每字符 2 估算，加上消息协议开销；视觉使用配置的每图预留，不按 Base64 长度计算视觉 Tokens。它是保守代理，未接部署模型精确 tokenizer，也没有误差上界保证。事件同时记录服务商实际用量与估算偏差，供后续校准。缓存命中内容仍占窗口，不能从预算扣除。

本地守卫不能证明服务商永远不会报超限，尤其在协议开销或视觉输入估算不完全一致时。应记录服务端 usage 与本地估算的偏差、调整安全量，并处理服务端超限返回。窗口计数针对单次完整请求，不是多次调用累计的 prompt_tokens。

轮数可以作为提取任务去抖或触发评测的辅助量，不能作为容量安全的唯一依据。只有两轮的长题目也可能超预算，二十轮简短对话却可能仍很小。

## 16 下一轮还没发生 怎么估计增长量

记预计在下一次检查前新增的输入量为 \(G\)，判断：

\[
T+G\geq0.90H
\]

成立时必须预防性处理。当前使用可配置的冷启动值和批次增长的指数平滑，工具增长初值默认 \(R_0=1024\)，设刚完成批次的工具回执与附图估算为 \(B_k\)：

\[
R_{k+1}=\max\left(256,\left\lfloor0.9R_k+0.1B_k\right\rfloor\right),\qquad
G=O+R_k\quad\text{（本次开放工具时）}.
\]

不开放工具的最终 JSON 请求取 \(G=0\)；若输出需要格式修复，下一轮仍按实际新增内容重新守卫。这是调度启发式，**不是 P95、不是工具结果绝对上界，也不是训练出的预测模型**。

预测是为了提前留出空间，不能替代发送前的实际计数。工具可能返回异常大的结果，所以工具结果落库并生成有上限的输入投影后，仍要重新计算 \(T\)。

检索工具已有有限摘录和条目投影，真实工具结果仍可能大于预测。当前靠逐调用守卫、旧记录摘要和必要时关闭下一批工具收口；更细的工具分页和按工具类型校准增长是后续优化，不能把它们说成已经覆盖全部工具。

这里的 \(G\) 包括尚未计入 \(T\)、将进入后续输入的 assistant 输出与工具回执，不重复计算已经追加的结果。\(O\) 预留当前输出，\(G\) 预测后续输入。例如 \(H=26624\)、\(G=4096\) 时，当前输入约 19866 就需要预防性处理，并非等到约 24k 才开始。

压缩后还要判断 \(T'+G<0.90H\)。当前先尝试降低本次输出预留，必要时关闭新工具，再重新选择无工具 JSON 的输出预留；requested/effective 值都有事件记录。仍不满足则受控结束，不松开 90% 判据，不无限压缩同一段历史。55% 是回落目标，不能承诺每次都达到。

## 17 怎样定义好的压缩时机 什么叫安全点

较好的时机同时满足：**容量有收益、业务片段相对完整、后续可以从已保存状态重建**。

典型安全点包括一次教学子任务结束、一次评估结果提交并记录清楚后续动作后、一个工具回路取得终态回执后，以及待答题已经保存并进入等待学生状态时。此时模型可以把已经结束的过程收成摘要，而当前执行契约仍然完整。

相反，模型已经发出有副作用的工具调用但尚未确认结果，或答案正在提交、目标更新还没落库时，不适合发布新检查点。先完成已有事务或查明工具结果，再基于新版本压缩。

并不需要等到整个会话结束。一个会话可以有很多安全点；“学习片段结束”是压缩边界，“会话结束”只是其中一个场景。

## 18 压缩怎样避免破坏 tool call 协议

按完整交互单元处理，而不是任意删除单条消息。一个单元可能包含 assistant 工具调用、对应的工具结果和必要的后续解释。

当前 `closed_message_groups` 将一次 assistant 的全部 tool_calls 和对应回执视为一个单元，支持回执乱序但要求 ID 完整匹配。还没被模型消费的最新结果、未闭合工具组不进入可替换前缀；必要题图像素保留。检查点保存 `source_units` 供重建，模型尚没有任意读取检查点原文的通用工具，不能把所有来源都说成已具备模型按需回读能力。

压缩不能触发工具重跑。尤其是提交作答、更新目标等写操作，摘要失败不意味着工具失败。回执状态不明时先按执行 ID 查询；没有结果查询能力的工具，属于需要补齐的恢复协议，不能靠让模型猜测“应该已经成功”补上。

“可重试的摘要生成”和“可能有副作用的教学工具执行”要使用不同的任务标识与重试策略。

## 19 具体怎样压缩 如何判断压得好

输入是可摘要的已提交原始历史与闭合工具组，当前目标、原题和待答状态另作为固定字段。模型输出 `topic_segments`、`confirmed_findings`、`uncertainties`、`unresolved_questions`、`source_refs`，不是一段自由作文。按最多24个来源一块生成阶段摘要，过长时再做一次有限合并，不无限递归。

每次摘要把顶层来源映射成 `s0`、`s1` 等短别名，并提供独立允许集合。模型必须完整覆盖这次的全部别名，不能缺项、加项或重复；校验通过后程序映回真实来源 ID。第二层合并只看阶段别名，底层来源映射保留在服务端，避免将嵌套来源误当作本层覆盖集合。服务商标记输出截断时也拒绝候选。

结构化状态由程序投影，摘要器没有修改目标或待答字段的入口。检查点保存源指纹、源原文、角色、规则版本、固定状态指纹与会话版本；来源覆盖不符、版本冲突、撤销屏障变化或没有输入回收收益时拒绝候选。来源完整不证明每个事实都被忠实表达，语义质量仍需抽检。

“压得好”至少有三个判断：

1. **容量达标**：通常收缩到目标水位，且实际输入不超预算；受当前必需内容限制时不强求固定压缩率。
2. **关键事实保持**：目标和返回位置一致、当前题准确、原始答案引用与帮助条件没有变化。
3. **行为仍可接续**：压缩后模型能继续正确的教学任务，不重复已完成步骤、不误判掌握、不激活旧目标。

前两类中有一部分可以确定性校验；第三类需要固定测试会话和人工抽样，不能只用另一个模型说“摘要完整”就算通过。模型复核可以提供额外信号，但不能充当唯一的发布条件。

不要无限执行“摘要的摘要”。保留原始记录和覆盖水位，必要时从已提交原文重建相应阶段，减少多轮压缩的误差积累。

## 20 如果当前题目本身很长 或压缩后还是超限怎么办

先判断超限来自哪里。

若来自旧对话、重复检索内容或不相关经历，可以进一步减少这些可选部分；若来自完整但很大的工具结果，保存原件并通过引用、分页或受限摘录读取必要部分。当前题目与真实答案不能被任意截断后继续做评估。

当前会把旧教学分析、旧 dialogue/evidence/support_history 和可选历史经历移入摘要；重复的记忆视图不重复注入，同一长原话通过带路径的 `verbatim_ref` 只保留一份。当前原话、原题、待答 ID、目标与提交前帮助条件保持完整，数据库原记录不变。

随后可以降低本次输出预留 \(O\)，从而提高 \(H\)，并在关闭工具后再次为最终 JSON 选择有效输出预算；这不需要扩大 \(C\)。每轮都记录 requested/effective 输出预算，避免上一轮降过预留、下一轮 JSON 修复又沿用过小的输入空间。当前固定内容仍不能满足预算和预防线时，就拒绝本次调用并要求分段，不能放行不完整答案继续评分。

摘要调用本身也有最终出口守卫、超时和有限分块。上下文压缩器当前会拒绝单个完整历史单元就超预算的情况，尚未实现任意长证明、代码或题目的自动自然分段；不能把记忆提取器的文本片段读取能力等同于完整题目分段求解。

## 21 学习经历摘要和上下文压缩摘要能共用吗

当前共用模型客户端和业务来源，但使用不同模块与输出契约：`domains/memory/extractor.py` 生成两类记忆，`agent/context/compactor.py` 生成本会话上下文摘要。

学习经历回答“这次学了什么、遇到了什么困难”，服务于以后相关会话的回顾；压缩检查点回答“当前执行到哪里、接下来如何接续”，服务于同一会话的下一次模型调用。前者可能在空闲时异步更新，后者需要与当前执行状态版本一致。

若直接把经历摘要当作全部运行上下文，容易丢掉待答题、工具回执和返回位置。若把完整运行检查点当作长期记忆，又会携带大量失效状态。因此可以共用原始来源，不能简单共用一段文本并让它承担所有责任。

## 22 多个任务同时更新记忆 怎样避免覆盖和重复

至少需要幂等键、来源水位和版本比较。

`MemoryFact` 对会话和来源设唯一约束；`MemoryJob` 以会话、水位、提取规则版本、结束版本构成唯一任务。学习经历以会话 ID 唯一，长期学生记忆以学生 ID 唯一。学生记忆和经历各自做版本比较，检查点另校验会话与来源状态，不能互相替代。

模型调用前读到版本 \(v\)，提交时只允许在当前版本仍为 \(v\) 的条件下更新到 \(v+1\)，也就是乐观并发控制。模型生成期间不持有长数据库事务。若版本已经变化，就读取新版与未覆盖证据重新合并，不能把旧输入生成的文本原样重试写回。

当前单进程 worker 对手动刷新和轮询共享领取锁，数据库任务持久保存状态、租约和重试；提交仍使用 CAS，跨会话结果不能拿旧版本覆盖新内容。它不是已经验证的分布式调度方案，也不承诺所有外部业务效果“恰好一次”。空闲与显式结束提交还检查事实水位和结束版本。

普通后台学生记忆或经历正文更新时，本轮可以继续使用已冻结且未撤销的快照，下轮再读新版；正文版本仍参与检查点缓存键。纠正或遗忘则立即使旧快照失效：检查当前会话的失效版本、学生撤销列表指纹，以及已加载历史经历各自的撤销指纹和会话失效版本。不能把普通增量更新误当作删除，也不能让撤销后的旧摘要复活。

## 23 模型失败 数据库失败 或摘要不可信时怎么处理

记忆提取通常可以异步重试。失败时保留旧的有效记忆，记录未处理水位和原因；当前教学可以使用旧记忆加当前已提交事实继续。服务端不能把提取异常解释为“没有新学习内容”。

上下文压缩失败则受输入预算限制：旧上下文仍满足预算与预防条件时可继续；否则只能收缩可选历史、调整输出预留、关闭新工具或受控停止。同一历史指纹最多两次摘要尝试，一次尝试可能包含多个分块模型调用，不能将它误说成总共只调用两次模型。服务商返回上下文超限时最多重建后重试一次，载荷没有实际变化就拒绝原样重试。

一旦新摘要校验通过并提交，切换版本应原子完成，避免读到半份摘要。工具结果和原始答案已经成功保存时，摘要任务失败只影响派生视图，不回滚或重跑业务写操作。

对被模型误写、来源不足或提示注入影响的摘要，应能撤回有效版本并重建。记忆是模型输入材料，其内容没有授权能力：不能因为画像写了“学生喜欢直接给答案”，就绕过评估规则或工具权限。

## 24 怎么评估系统有效 怎样解释阈值选择

当前已有固定学习轨迹、专项断言和独立数据库上的真实后端验收脚本。学生输入明确为脚本模拟，教学、记忆和摘要调用实际配置模型；它验证调用链和工程不变量，不代表真实学生学习实验。最终报告以 [实现说明](../stem_v1/17_memory_and_context_implementation.md) 为准。

后续还需对旧裁剪、仅摘要、结构化状态加摘要做受控比较，并人工标注语义遗漏，才能校准默认参数和判断总成本；这项效果比较尚不能作为已完成成果陈述。

| 评估维度 | 重点指标或断言 |
|---|---|
| 容量 | 实际输入 Token、超预算拦截、压缩触发频率、压缩后体积 |
| 开销 | 摘要耗时、首字延迟变化、额外摘要 Token、总调用成本 |
| 状态保持 | 当前目标和待答题一致率、返回位置保持、重复教学和旧目标误激活 |
| 学习证据 | 真实答案引用、帮助条件保持，是否出现“讲过等于掌握”的错误 |
| 记忆质量 | 事实来源支持、重复率、纠正成功、删除后是否重新出现 |
| 恢复与隔离 | 任务重试、并发冲突、版本过期、跨学生信息混入 |

测试轨迹应覆盖长对话、临时补基础、明确换目标、长工具输出、工具超时、等待学生答题、并发写入，以及多次压缩后的漂移。关键状态要求使用可执行断言；语义遗漏使用人工标注或有依据的复核。

70%、90%、55% 的意义分别是“提前寻找合适时机”“留下下一轮增长余量”“形成足够回滞空间”。它们是可解释的初始控制参数，最优值取决于实际消息分布、工具输出和模型表现。没有回放数据就应说“待校准”，不能说“行业通用最优”。

记忆的质量与教学效果也不能画等号。摘要更完整不必然提升长期学习成绩，后者需要独立的教学效果评估。

## 25 简历和面试中哪些表述容易说过头

| 容易误导的说法 | 更准确的说法 |
|---|---|
| 实现了完整长期记忆系统 | 已实现两类轻量模型记忆的提取、维护与读取，并有专项和真实链路验证；语义质量、分布式调度及默认参数仍有边界 |
| 通过压缩保证零信息损失 | 对关键控制状态做一致性校验，对语义摘要通过回放和抽样衡量遗漏 |
| 自动总结就能记住所有内容 | 只保留符合用途的短记忆，原始记录仍可回查 |
| 目标树跨会话自动延续 | 目标树只在当前会话内维护，旧会话经历可供新目标参考 |
| 摘要能够恢复整个 Agent | 运行恢复依赖持久化业务状态、工具回执和版本；摘要辅助模型理解 |
