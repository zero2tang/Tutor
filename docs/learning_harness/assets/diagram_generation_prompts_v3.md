设计约束：每图只展开一个层级；用有标签的分支说明关键条件；主流程和旁路分开；不把流程完成当成掌握，不把工具回调画成静态依赖倒置。

```text
Use case: infographic-diagram
用途：中文后端架构学习文档，读者理解基本编程但并非资深架构师。根据指定内容重绘成可准确学习的图，增加必要细节但不堆砌文字。
统一视觉规范：横向约 3:2 画幅，高分辨率；纯白背景、深蓝灰正文、清晰中文无衬线字体。标题一级、模块名二级、说明三级。细线、轻微圆角、等距对齐；小模块至多标题加两行说明，重要限制放独立短注。蓝色用于执行与请求，绿色用于业务事实与事务，低饱和紫色用于派生记忆，灰色虚线用于投影或辅助关系。回路用带文字标签的细线，允许少量灰色容器分组。留白充足但不要把图缩成空洞的几个框。

副标题：“业务决定目标，模型选择动作，服务提交事实”
布局：顶部业务编排；中央 Runtime 大容器，Agent loop 在容器中央；Runtime 底部为深蓝纯色执行基座；左右是输入、能力、状态与输出。整体阅读顺序从上到中央，再到左右。
顶部模块：“业务编排”；说明“LearningService / GuidedTeachingService”“目标流程 · 会话占用 · 请求幂等”；箭头进入 Runtime。
中央 Runtime 内部画五个紧凑节点：
A“上下文准备”，说明“预算检查 · 来源验证”；
B“模型决策”，说明“请求模型，处理响应”；
C“工具调度”，说明“授权 · 参数 · 并发限制”；
D“追加回执”，说明“按 tool_call_id 配对”；
E“结果校验”，说明“JSON · Schema · 业务条件”。
必须连 A→B；B→C 标“有工具调用”；C→D→A，构成清晰闭环；B→E 标“候选结果”；E→A 用细回路标“可修正反馈”。E 通过后交回右侧业务服务。不要把 E 放进所有工具调用都必经的循环。
底部基座：“Runtime 执行保障”；说明“父子 run · 输入预算 · 工具限制”“超时与取消 · 用量与运行记录”。

“业务状态与记忆”：“会话 / 目标 / 待答题”“作答证据 / 掌握状态 / 来源记忆”；虚线进入A。
“审计与恢复”：“AgentRun / RunEvent”“幂等回放 / 已完成委派产物”；与 Runtime 用灰色辅助线关联。短注“业务回放 ≠ 调用栈恢复”。
```
