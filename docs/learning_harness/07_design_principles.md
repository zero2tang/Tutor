# 07 · 从当前实现理解设计取舍

判断一个机制是否有价值，要问：它接收什么、由谁授权、能改变什么、失败后留下什么。框架替换没有改变这些问题。

## 1. 模型提出行动，领域服务决定能否提交

Plan、Lesson 和 Diagnosis 是提案。目录范围、题目可用性、目标版本、帮助条件和证据资格由服务检查。Prompt 和 Skill 描述方法，真实工具及领域事务执行权限。

\[
\text{允许操作}=\text{角色可见能力}\cap\text{可信业务范围}\cap
\text{当前状态可执行动作}\cap\text{剩余预算}.
\]

项目没有一个计算全部规则的通用策略引擎。不同规则留在拥有对应事实的业务边界。

## 2. 委派必须闭环

“建议另一个 Agent 出题”不是执行。真实 @tool 等待子任务，回传产物和运行引用，原 create_agent 继续消费 ToolMessage。父与子使用隔离上下文并共享根预算，不通过复制父消息取得权限。

## 3. 图节点需要理由

只有分支、并发或恢复边界才上图。评分候选与正式事务分成节点，是为了避免提交故障后重复昂贵诊断；普通目录查询、公开投影和评分规则仍是函数。

习题三步图体现质量分支，Send 体现多题并发。把每个业务函数包装为节点，会增加状态和恢复面，不能因为框架支持就全部图化。

## 4. 原始事实、执行状态和推导分开

\[
C_t=\operatorname{Project}(\text{当前任务},\text{正式事实},\text{有效记忆},\text{必要执行历史}).
\]

上下文是投影。消息被摘要压缩，不等于删除学生原答；checkpoint 中存在某个目标投影，也不等于它可以覆盖更新后的正式目标。证据和长期记忆分别归领域服务管理。

## 5. 慢模型与短事务分开

模型请求期间不占用长期写事务。每次正式写入在自己的事务中重新确认 owner 和适用版本，不能把节点之前的检查当成事务内授权。

单 worker 的 active_turn_id 与数据库启动锁不构成分布式租约。SQLAlchemy、Saver 和 Store 的独立提交通过正式回执及发布指针核对恢复。

## 6. 正式效果可重放

稳定 operation_id 与输入指纹绑定同一效果。已生成题、已发布消息、已提交评分优先查正式回执，失败后重试不应增加同一业务效果：

\[
\text{重复请求次数增加}\ \not\Rightarrow\ \text{同一证据重复累积}.
\]

这不等于任意崩溃点的通用 exactly-once 证明；它依赖具体事务和回执。新输入可终止已释放执行权的旧计算，但真实原答及已提交结果继续保留。

## 7. 学习正确性不能由框架背书

同模型独立求解与语义复核可能产生相关错误。讲解完成不是掌握，辅助作答不是独立证据，模型置信度也不是校准概率。原题、步骤、帮助和证据来源的可追溯性比堆叠 Agent 名称更重要。

## 8. 简化需要删除证据

标准模型和真实工具已经接入，但旧注册表、消息推进器和控制器仍主要存在，就不能称为完成。当前物理删除、薄保留和新增恢复成本见[30 号记录](../stem_v1/30_native_remaining_implementation_and_acceptance.md)；移动文件和压缩排版不计为简化收益。
